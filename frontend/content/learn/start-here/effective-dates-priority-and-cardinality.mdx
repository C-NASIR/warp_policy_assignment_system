## First choose the effective version

Policy versions have inclusive start and end dates. For an evaluation date, PolicyOS considers the version whose range includes that date. Versions of the same policy cannot overlap, and a date in a gap gets no behavior from that policy.

California Pay Schedule version 1 assigns **Bi-weekly**. Scheduling version 2 for October 1, 2026 with **Weekly** closes an open-ended version 1 on September 30. On September 30, version 1 applies; on October 1, version 2 applies.

## Then resolve each field

For a **one-value** field, the highest-priority candidate wins. Avery has two pay candidates:

| Policy | Candidate | Priority | Result |
| --- | --- | ---: | --- |
| California Pay Schedule | Bi-weekly | 20 | Selected |
| US Employee Pay | Semi-monthly | 10 | Not selected |

Both policies match, but only Bi-weekly becomes the Pay schedule assignment. Match and selection are different decisions.

For a **many-value** field, PolicyOS retains unique values from all candidates. Security Baseline contributes 1Password directly; Engineering Access contributes GitHub and Linear through the Engineering group. Avery receives all three.

If multiple sources contribute the same many-value result, PolicyOS keeps one copy and records the preferred source: highest priority first, then the lowest version ID as the stable tie-breaker.

## A deliberate stop

If different values compete at the same highest priority for a one-value field, PolicyOS reports a conflict instead of choosing arbitrarily. An author must change the priority or remove unintended rule overlap before resolution can continue.
