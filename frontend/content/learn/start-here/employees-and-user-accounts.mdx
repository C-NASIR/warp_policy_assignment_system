## Two records, two jobs

An **employee record** represents a person in the workforce. It holds trusted facts—such as state, department, employee type, start date, location, and manager—that policies can evaluate. PolicyOS can calculate assignments for an employee even if that person never signs in.

A **user account** represents an identity that can sign in. It has credentials, roles, permissions, and security settings. An account may be linked to an employee, but the two records remain separate.

## Avery exists before Avery can sign in

A people operator first creates Avery Chen as an employee:

| Employee fact | Value |
| --- | --- |
| State | California |
| Department | Engineering |
| Employee type | Full-time |
| Location | San Francisco |
| Start date | September 14, 2026 |
| Manager | Maya Patel |

Those facts are enough for policies to calculate Avery's pay schedule, vacation policy, compliance training, application access, and equipment stipend.

Later, an access administrator creates `avery.chen@example.test` and links it to Avery's employee record. The link makes policy-derived roles possible. Without it, Avery can still have assignments, but there is no sign-in identity to receive an automated role.

## What the link does not do

Linking an account does not turn every assignment into a permission. A policy can grant only a role that is explicitly eligible for automation. Manually assigned roles stay separate and are not removed when policy results are reconciled.

If you can read employee data but cannot manage access, you can still understand the distinction; an access administrator performs the account and role steps.
