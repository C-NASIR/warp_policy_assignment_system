Root has been running the workspace alone. Morgan now needs to maintain employee information, so Root will give Morgan a defined responsibility instead of sharing the Root account.

Open **Access control** through Quick find's **Manage access** command or the link below. The page separates **Roles**, which define responsibilities, from **Users**, who can sign in.

## Define the responsibility first

On **Roles**, create a role named **People operator**. This is a role we are configuring for the example company, not a built-in PolicyOS role.

Give it the permissions needed to view, create, and update employees and to preview supported employee changes. Add assignment-reading permission only if Morgan must inspect the resulting assignments. Do not add policy, access-management, approval, or execution permissions merely because Morgan's company job title sounds administrative.

For this first delegation, choose all employees as the employee scope and all assignment fields if Morgan genuinely supports the whole organization. The next lesson replaces those broad choices with narrower examples.

Before saving, read the form as one access statement:

> A People operator may perform these selected actions, for these employees, in these assignment domains.

Role changes are sensitive operations. The form asks the current administrator to re-enter a password and, when enabled, an MFA code. The role saves directly; this action does not enter the policy approval queue.

## Provision Morgan's account

On **Users**, create Morgan's user with the intended email, a temporary password of at least 12 characters, and the People operator role. A non-Root user must have at least one role.

Link Morgan to Morgan's employee record only if that record exists and later self or reporting-tree scope should start from Morgan. Account creation does not create the employee record, and the employee link does not add permissions.

After saving, verify the Users row:

- Morgan is active.
- People operator appears as an assigned role.
- The employee link is correct or deliberately empty.
- The effective permission count matches the intended responsibility.

Morgan must change the temporary password at first sign-in. Until then, PolicyOS blocks normal application operations. Test the resulting access with Morgan's account; Root's view cannot demonstrate what Morgan can see.

An account's name and email identify the user. Morgan's authority comes from all assigned roles, not from the name “People Operations.” If another role is later added, its permissions and scopes broaden Morgan's effective access.
