Morgan is acting as a Policy author. Jordan is the independent Reviewer. These are example roles configured by the company; the permissions assigned to them create the separation of duties.

Morgan needs policy-reading and version-authoring authority, activation authority when changing an active policy, and change-preview permission. Jordan needs approval and execution permissions plus the policy authority required to execute the proposed version or lifecycle change.

Use separate signed-in accounts in a connected training deployment.

## Morgan submits the exact proposal

Open the future vacation version prepared in [Schedule a policy change](/learn/policyos/schedule-a-policy-change). Morgan checks the effective date, priority, conditions, and assignment values, then chooses **Preview impact**.

For an ordinary signed-in author, previewing a policy version submits a persisted request instead of exposing **Create version**. The page shows the request ID and an **Open approvals** link. The request records the exact proposal and calculated assignment impact; the policy version has not been created.

Morgan gives Jordan the request ID through the team's normal handoff process. The application does not send a message or email, assign the request to a named reviewer, or provide a dedicated request-search box.

## Jordan reviews and decides

Jordan opens **Approvals** and finds the card using its type, requester, time, and **Request ID**.

1. Check **Assignment impact** and **Expires**.
2. Expand **View exact proposed change**. Verify the policy, effective dates, priority, conditions, and assignment values.
3. Choose **Reject** if the proposal should stop. Rejection ends this request; Morgan must submit a new proposal after making corrections.
4. Choose **Approve** only if this exact proposal may proceed.

Morgan cannot approve or reject Morgan's own request even if Morgan's other roles include approval permission. Jordan's buttons also depend on request status and permissions.

## The approver executes

Approval alone does not save the version. After approval, Jordan chooses **Execute approved change**. For an ordinary user, the approving user must perform this step and must hold execution permission and the policy authority needed by the change.

Root is a privileged exception: Root can execute an approved request even when another user approved it. Root's own policy previews do not create the ordinary pending human request; when the supported screen offers direct execution, Root can commit the signed preview without independent review.

Execution verifies the approval has not expired and that both the proposal's target state and calculated impact still match what was reviewed. If either is stale, return to the originating policy workflow and create a fresh preview and approval request.

After successful execution, the request status is **executed** and the version appears in **Version history**. A future effective date still governs when the new version participates. Today's assignment may remain unchanged, and scheduled reconciliation must run when the date arrives before stored current assignments reflect future behavior.

Normal employee edits, group membership changes, policy lifecycle changes, and override confirmations do not automatically appear here. A missing permission for some other action does not create an approval route.

Demo mode cannot complete this workflow.
